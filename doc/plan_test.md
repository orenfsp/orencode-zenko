# План проверки backend

## 1. Запуск

```bash
docker compose up -d postgres migrate rbac-seed seed-demo server
docker compose logs migrate server
```

Проверить отсутствие ошибок миграций и запуска API.

Подготовить access-токены для администратора, участника, тренера и судьи.

## 2. Permissions

```http
GET /api/v1/my-permission
Authorization: Bearer <token>
```

Ожидаемые права:

- `admin` и `super_admin` — все permissions;
- `coach` — `teams.manage`;
- `judge` — `competition_results.read`, `competition_results.manage`;
- `participant` — без административных permissions.

## 3. Доступ участника

Проверить под токеном участника:

```http
GET /api/v1/profile
GET /api/v1/rank-applications/mine
GET /api/v1/ranks/history
GET /api/v1/profile/competition-results
GET /api/v1/notifications
```

Ожидается доступ только к собственным данным. Доступ к административным ручкам должен возвращать `403`.

## 4. Роли и permissions

Под участником проверить:

```http
GET /api/v1/admin/roles
GET /api/v1/admin/permissions
GET /api/v1/admin/dashboard
```

Ожидается `403 Forbidden`.

Под администратором эти ручки должны работать.

## 5. Тренер и спортсмены

1. Создать связь тренер–спортсмен.
2. Подтвердить связь.
3. Создать заявку на разряд за подтверждённого спортсмена.
4. Попробовать создать заявку за неподтверждённого спортсмена.

Ожидается: подтверждённая связь разрешает операцию, неподтверждённая возвращает `403`.

## 6. Сборные команды

```http
POST /api/v1/admin/teams
GET /api/v1/admin/teams
```

Проверить:

- тренер указан в `coach_ids`;
- участники имеют подтверждённую связь с тренером;
- неподтверждённый спортсмен отклоняется;
- тренер видит только свои сборные;
- администратор видит все сборные;
- участник не может создавать сборные.

## 7. Судья и результаты

1. Назначить судью на соревнование.
2. Судьёй открыть результаты назначенного соревнования.
3. Попробовать открыть результаты другого соревнования.
4. Проверить сохранение, расчёт и утверждение результатов.

Ожидается: назначенное соревнование доступно, неназначенное возвращает `403`, администратор имеет полный доступ.

## 8. Рейтинг

```http
GET /api/v1/admin/rating?year=2026&discipline_id=2&municipality_id=3
```

Проверить:

- учитываются только результаты `finished`;
- работают фильтры;
- сортировка идёт по сумме баллов;
- `score` имеет приоритет над баллами за место.

## 9. ЕВСК

Создать норматив:

```http
POST /api/v1/admin/rank-standards
```

Проверить одобрение заявки на разряд:

- соответствующий нормативу результат — `approved`;
- несоответствующий результат — `422`;
- при ошибке записи о разряде нет.

## 10. Дедлайны

```http
GET /api/v1/deadlines
POST /api/v1/admin/report-deadlines
PATCH /api/v1/admin/report-deadlines/{id}
```

Для `governor_award` проверить:

- `2027-02-01` принимается;
- `2027-02-02` отклоняется;
- уведомление получают администраторы;
- напоминания создаются за 7 и 1 день.

## 11. Файлы и XLSX

```http
GET /api/v1/admin/files
GET /api/v1/admin/reports/users.xlsx
GET /api/v1/files/{fileID}/download
```

Проверить:

- администратор видит список файлов;
- XLSX скачивается и открывается;
- пользователь не скачивает чужой файл;
- в ответе отчёта присутствует `X-File-ID`.

## 12. Итоговая проверка

```bash
go test ./...
docker compose logs migrate server
```

Зафиксировать для каждого сценария: запрос, токен/роль, HTTP-код, фактический ответ и результат проверки.
