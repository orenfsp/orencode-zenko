# API результатов соревнований и протоколов

Модуль хранит черновик зачёта отдельно для каждого `competition_event`, поддерживает автоматический алгоритмический и ручной зачёт по повторно используемому шаблону, утверждает итог и формирует PDF-протокол. Успешные административные ответы имеют вид `{"data": ...}`, ошибки — `{"code":"...","message":"..."}`; см. [общий контракт ошибок](./mvp-backend-api.md#формат-ошибок-основных-api).

## Разрешения

- `competition_results.read` — просмотр таблицы;
- `competition_results.manage` — настройка, ввод и расчёт черновика;
- `competition_results.approve` — утверждение зачёта.

Для маршрутов таблицы результатов дополнительно применяется проверка роли: пользователь должен быть `admin`/`super_admin` либо назначенным на это соревнование судьёй с соответствующим permission. Загрузка и удаление протокола проверяют только `competition_results.approve`.

После обновления приложения следует повторно запустить существующий seed RBAC (`go run ./cmd/seed-rbac`), чтобы зарегистрировать разрешения и выдать их системным ролям `super_admin` и `admin`.

## Маршруты

### Шаблоны ручного зачёта

Маршруты чтения требуют `competition_results.read`, изменения — `competition_results.manage`:

- `POST /api/v1/admin/result-templates` — создание;
- `GET /api/v1/admin/result-templates?discipline_id={id}` — список шаблонов дисциплины;
- `GET /api/v1/admin/result-templates/{id}` — получение шаблона;
- `PATCH /api/v1/admin/result-templates/{id}` — изменение или деактивация через `is_active=false`.

```json
{
  "discipline_id": 4,
  "name": "Оценка проектов ИИ",
  "fields": [
    {"key":"quality","label":"Качество модели","type":"number","required":true},
    {"key":"comment","label":"Комментарий судьи","type":"text","required":false}
  ]
}
```

Поддерживаются типы `number` и `text`, от 1 до 12 упорядоченных полей. `key` начинается с латинской строчной буквы и содержит только `[a-z0-9_]`; ключи уникальны. Название шаблона и label ограничены 200 символами, текстовое значение — 2000 символами. Удаление не предусмотрено. Редактирование исходного шаблона не меняет уже настроенный зачёт: структура сохраняется в snapshot.

### Настройка индивидуального зачёта

`PUT /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/settings`

```json
{
  "mode": "individual",
  "scoring_mode": "algorithmic",
  "task_count": 12
}
```

Строки создаются для всех заявок мероприятия со статусом `approved`. Повторная настройка неутверждённого зачёта пересоздаёт строки и очищает ранее введённые результаты. Допустимо от 1 до 50 задач.

### Настройка командного зачёта

```json
{
  "mode": "team",
  "task_count": 12,
  "teams": [
    {
      "team_id": 7,
      "application_ids": [101, 102, 103]
    }
  ]
}
```

Каждая одобренная заявка должна быть указана ровно один раз. Спортсмен из заявки должен состоять в указанной команде на дату начала соревнования. Числовые ID берутся из БД/API, а не фиксируются во frontend.

### Настройка ручного зачёта

Используется тот же `PUT .../results/settings`:

```json
{
  "mode": "individual",
  "scoring_mode": "manual",
  "task_count": 0,
  "template_id": 5,
  "confirm_reset": false
}
```

Шаблон должен существовать, быть активным и относиться к дисциплине мероприятия. Backend сохраняет `template_snapshot` (ID, название и поля). Последующее редактирование шаблона snapshot не меняет. Смена режима, состава или шаблона существующего черновика требует `confirm_reset:true`; утверждённый зачёт менять нельзя. Командный ручной зачёт использует тот же массив `teams`.

### Получение таблицы

`GET /api/v1/admin/competitions/{competitionID}/events/{eventID}/results`

```json
{
  "data": {
    "competition": {"id": 4, "name": "Чемпионат области"},
    "event": {
      "id": 7,
      "discipline_id": 1,
      "discipline_name": "программирование алгоритмическое",
      "age_group_name": "юниоры"
    },
    "mode": "individual",
    "task_count": 0,
    "status": "draft",
    "revision": 0,
    "scoring_mode": "manual",
    "template_id": 5,
    "template_snapshot": {
      "id": 5,
      "name": "Оценка проектов ИИ",
      "fields": [{"key":"quality","label":"Качество модели","type":"number","required":true}]
    },
    "calculated_at": null,
    "approved_at": null,
    "protocol_url": null,
    "entries": []
  }
}
```

У каждой строки есть `team` (либо `null`), массив `participants`, `result_status`, результаты задач, рассчитанные показатели, `place` и `custom_values`. Пустые массивы сериализуются как `[]`. Поле `revision` меняется после записи и защищает ручной ввод от конкурентной перезаписи.

### Сохранение черновика

`PUT /api/v1/admin/competitions/{competitionID}/events/{eventID}/results`

Можно передать одну или несколько изменённых строк:

```json
{
  "entries": [
    {
      "entry_id": 55,
      "result_status": "finished",
      "tasks": [
        {
          "task_number": 1,
          "status": "solved",
          "solve_time_deciseconds": 1234,
          "negative_attempts": 1
        },
        {
          "task_number": 2,
          "status": "attempted",
          "solve_time_deciseconds": null,
          "negative_attempts": 2
        }
      ]
    }
  ]
}
```

Статусы задачи: `not_attempted`, `attempted`, `solved`. Время положительного решения хранится в десятых долях секунды и обязательно только для `solved`. Статусы строки: `finished`, `did_not_start`, `disqualified`. У двух последних массив `tasks` должен быть пустым.

### Сохранение ручного результата

`PUT /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/manual`

```json
{
  "revision": 0,
  "entries": [
    {"entry_id":101,"result_status":"finished","place":1,
     "custom_values":{"quality":92.5,"comment":"Отличная работа"}},
    {"entry_id":102,"result_status":"did_not_start","place":null,"custom_values":{}}
  ]
}
```

Запрос передаёт полный набор строк и текущий `revision` из GET; изменения фиксируются одной транзакцией. Неизвестные ключи, неверные типы, пропуск обязательного поля, повторный `entry_id`, неположительное или одинаковое место отклоняются. Для `did_not_start` и `disqualified` место должно быть `null`. Устаревший `revision` даёт `409`.

### Расчёт итогов

`POST /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/calculate`

Для алгоритмического программирования строки сортируются последовательно по:

1. количеству решённых задач (больше — выше);
2. суммарному времени положительных решений (меньше — выше);
3. времени последней решённой задачи (меньше — выше);
4. числу отрицательных решений (меньше — выше).

Полностью равные результаты получают одинаковое место, следующее место пропускается (например, `1, 1, 3`). `did_not_start` располагается после завершивших зачёт, `disqualified` — после не стартовавших. Место сохраняется для каждой строки. Для иных дисциплин в режиме `algorithmic` API возвращает `422`. В режиме `manual` маршрут только проверяет поля, статусы и места; ручные места не пересчитываются.

### Утверждение

`POST /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/approve`

Утверждение повторно рассчитывает алгоритмический итог либо валидирует ручной итог, одной транзакцией фиксирует зачёт, создаёт/обновляет `competition_result` для каждой связанной заявки и записывает ссылку в `competition_event.protocol_url`. В ручном режиме `score` остаётся `NULL`, место сохраняется без выдуманной формулы. Повторный запрос идемпотентен. После утверждения настройка и редактирование запрещены.

Если после настройки изменился набор одобренных заявок, утверждение возвращает `409`: таблицу нужно настроить заново, чтобы ни один спортсмен не был пропущен и отклонённая заявка не попала в итог.

```json
{
  "data": {
    "status": "approved",
    "approved_at": "2026-10-27T15:00:00Z",
    "protocol_url": "/api/v1/competitions/4/events/7/protocol"
  }
}
```

Для команды одинаковые `place`, `score` (число решённых задач) и `result_status` записываются в существующую `competition_result` каждой заявки состава. Поэтому результат появляется в истории каждого спортсмена и остаётся совместимым с разрядами.

### Получение протокола

`GET /api/v1/competitions/{competitionID}/events/{eventID}/protocol`

Публичный маршрут доступен только после утверждения и возвращает `application/pdf`. PDF хранится через существующий `LocalStorage` в каталоге `protocols/`, но не регистрируется как приватный пользовательский документ в `uploaded_file`.

Демонстрационный seed записывает ключ `demo/protocol.pdf` и URL `/api/v1/files/demo/protocol.pdf`, но сам файл протокола не создаёт. Поэтому наличие этих полей в демо-БД не подтверждает доступность PDF через публичный маршрут; реальный протокол создаётся при утверждении результатов или загружается описанным ниже PUT.

Алгоритмический PDF сохраняет прежнюю таблицу задач и итогов. Ручной PDF строится по snapshot и содержит название шаблона, поля в заданном порядке, места и статусы; широкие шаблоны разбиваются на секции страниц. Оба варианта поддерживают кириллицу и содержат соревнование, дисциплину, возрастную группу, дату, главного судью и секретаря, если они назначены.

### Загрузка, замена и удаление PDF

Сотрудник с permission `competition_results.approve` может загрузить собственный PDF для уже утверждённого зачёта:

```bash
curl -X PUT 'http://localhost:8080/api/v1/admin/competitions/4/events/7/protocol' \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -F 'file=@protocol.pdf;type=application/pdf'
```

Тело — `multipart/form-data` с единственным файловым полем `file`. Принимается содержимое с заголовком `%PDF-` и маркером `%%EOF` в последних 1024 байтах, максимальный размер файла — 20 МиБ. Имя и MIME, переданные клиентом, не используются как подтверждение формата и не определяют путь хранения. Успешный ответ `200`:

```json
{"data":{"protocol_url":"/api/v1/competitions/4/events/7/protocol"}}
```

Повторный PUT заменяет текущий документ: сначала создаётся новый файл, затем две ссылки обновляются одной транзакцией. При неуспешном сохранении прежний протокол остаётся доступным. После фиксации прежний файл удаляется; если удаление файла в хранилище завершилось ошибкой, API сохраняет новую ссылку, а ошибка записывается в журнал (неиспользуемый файл может остаться на диске).

```bash
curl -X DELETE 'http://localhost:8080/api/v1/admin/competitions/4/events/7/protocol' \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

Успешное удаление возвращает `204`; ссылка и ключ очищаются, публичный GET возвращает `404`. Результаты и статус утверждения не меняются. Новый PUT снова публикует протокол. Утверждение результатов по-прежнему выполняется отдельным существующим маршрутом и при первом утверждении генерирует PDF автоматически; загрузка файла не утверждает зачёт. При повторном вызове утверждения после удаления протокола возвращается `404`, а не ссылка на отсутствующий файл.

Ошибки загрузки и удаления: `400` — некорректный multipart или содержимое PDF; `401` — нет токена; `403` — нет permission; `404` — мероприятие или удаляемый протокол не найден; `409` — зачёт не утверждён; `413` — PDF больше 20 МиБ; `500` — ошибка БД или хранилища.

## Коды ответа

- `200` — успешный запрос;
- `400` — неверный ID, JSON, состав команды или результаты задачи;
- `401` — нет access-токена;
- `403` — нет нужного permission;
- `404` — соревнование/мероприятие/таблица/протокол не найден;
- `409` — утверждённый зачёт, устаревший `revision` или сброс без `confirm_reset`;
- `422` — неподходящий режим, неактивный/чужой шаблон или неподдерживаемый автоматический расчёт;
- `500` — внутренняя ошибка без раскрытия деталей БД.

## Изменения данных

Миграция `019_competition_event_results` добавляет базовые таблицы зачёта. Миграция `033_result_templates` добавляет:

- `discipline_result_template` — повторно используемые шаблоны;
- `competition_event_result_sheet.scoring_mode`, `template_id`, `template_snapshot`;
- `competition_event_result_entry.custom_values`.

Старые строки получают `scoring_mode=algorithmic`; формула и PDF не меняются. Для `manual` разрешён `task_count=0`, для `algorithmic` сохраняется диапазон 1–50. DOWN отказывается выполняться при наличии ручных зачётов, чтобы не потерять их данные молча.
