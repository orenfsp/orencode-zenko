# API результатов соревнований и протоколов

Модуль хранит черновик зачёта отдельно для каждого `competition_event`, рассчитывает места для дисциплины «программирование алгоритмическое», утверждает итог и формирует PDF-протокол. Все административные ответы имеют вид `{"data": ...}`, ошибки — `{"message":"..."}`.

## Разрешения

- `competition_results.read` — просмотр таблицы;
- `competition_results.manage` — настройка, ввод и расчёт черновика;
- `competition_results.approve` — утверждение зачёта.

После обновления приложения следует повторно запустить существующий seed RBAC (`go run ./cmd/seed-rbac`), чтобы зарегистрировать разрешения и выдать их системной роли `super_admin`.

## Маршруты

### Настройка индивидуального зачёта

`PUT /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/settings`

```json
{
  "mode": "individual",
  "task_count": 12
}
```

Строки создаются для всех заявок мероприятия со статусом `approved`. Повторная настройка неутверждённого зачёта пересоздаёт строки и очищает ранее введённые результаты. Допустимо от 1 до 50 задач.

### Настройка командного зачёта

```json
{
  "mode": "team",
  "task_count": 12,
  "teams": [
    {
      "team_id": 7,
      "application_ids": [101, 102, 103]
    }
  ]
}
```

Каждая одобренная заявка должна быть указана ровно один раз. Спортсмен из заявки должен состоять в указанной команде на дату начала соревнования. Числовые ID берутся из БД/API, а не фиксируются во frontend.

### Получение таблицы

`GET /api/v1/admin/competitions/{competitionID}/events/{eventID}/results`

```json
{
  "data": {
    "competition": {"id": 4, "name": "Чемпионат области"},
    "event": {
      "id": 7,
      "discipline_id": 1,
      "discipline_name": "программирование алгоритмическое",
      "age_group_name": "юниоры"
    },
    "mode": "individual",
    "task_count": 12,
    "status": "draft",
    "calculated_at": null,
    "approved_at": null,
    "protocol_url": null,
    "entries": []
  }
}
```

У каждой строки есть `team` (либо `null`), массив `participants`, `result_status`, результаты задач, рассчитанные показатели и место. Пустые массивы сериализуются как `[]`.

### Сохранение черновика

`PUT /api/v1/admin/competitions/{competitionID}/events/{eventID}/results`

Можно передать одну или несколько изменённых строк:

```json
{
  "entries": [
    {
      "entry_id": 55,
      "result_status": "finished",
      "tasks": [
        {
          "task_number": 1,
          "status": "solved",
          "solve_time_deciseconds": 1234,
          "negative_attempts": 1
        },
        {
          "task_number": 2,
          "status": "attempted",
          "solve_time_deciseconds": null,
          "negative_attempts": 2
        }
      ]
    }
  ]
}
```

Статусы задачи: `not_attempted`, `attempted`, `solved`. Время положительного решения хранится в десятых долях секунды и обязательно только для `solved`. Статусы строки: `finished`, `did_not_start`, `disqualified`. У двух последних массив `tasks` должен быть пустым.

### Расчёт итогов

`POST /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/calculate`

Для алгоритмического программирования строки сортируются последовательно по:

1. количеству решённых задач (больше — выше);
2. суммарному времени положительных решений (меньше — выше);
3. времени последней решённой задачи (меньше — выше);
4. числу отрицательных решений (меньше — выше).

Полностью равные результаты получают одинаковое место, следующее место пропускается (например, `1, 1, 3`). `did_not_start` располагается после завершивших зачёт, `disqualified` — после не стартовавших. Место сохраняется для каждой строки. Для иных дисциплин API возвращает `422`, не применяя неподходящую формулу.

### Утверждение

`POST /api/v1/admin/competitions/{competitionID}/events/{eventID}/results/approve`

Утверждение повторно рассчитывает итог, одной транзакцией фиксирует зачёт, создаёт/обновляет `competition_result` для каждой связанной заявки и записывает ссылку в `competition_event.protocol_url`. Повторный запрос идемпотентен. После утверждения настройка и редактирование запрещены.

Если после настройки изменился набор одобренных заявок, утверждение возвращает `409`: таблицу нужно настроить заново, чтобы ни один спортсмен не был пропущен и отклонённая заявка не попала в итог.

```json
{
  "data": {
    "status": "approved",
    "approved_at": "2026-10-27T15:00:00Z",
    "protocol_url": "/api/v1/competitions/4/events/7/protocol"
  }
}
```

Для команды одинаковые `place`, `score` (число решённых задач) и `result_status` записываются в существующую `competition_result` каждой заявки состава. Поэтому результат появляется в истории каждого спортсмена и остаётся совместимым с разрядами.

### Получение протокола

`GET /api/v1/competitions/{competitionID}/events/{eventID}/protocol`

Публичный маршрут доступен только после утверждения и возвращает `application/pdf`. PDF хранится через существующий `LocalStorage` в каталоге `protocols/`, но не регистрируется как приватный пользовательский документ в `uploaded_file`.

Протокол содержит соревнование, мероприятие, дисциплину, составы, задачи, итоги, статистику, назначенных главного судью и главного секретаря, дату и незаполненные места подписей/печати. Если должность не назначена, остаётся пустое поле; фиктивная подпись не создаётся. Так как актуальная `competition_event` не имеет отдельного поля названия, в документе используется «Мероприятие №{id}» и возрастная группа.

## Коды ответа

- `200` — успешный запрос;
- `400` — неверный ID, JSON, состав команды или результаты задачи;
- `401` — нет access-токена;
- `403` — нет нужного permission;
- `404` — соревнование/мероприятие/таблица/протокол не найден;
- `409` — попытка изменить утверждённый зачёт;
- `422` — правила расчёта дисциплины пока не реализованы;
- `500` — внутренняя ошибка без раскрытия деталей БД.

## Изменения данных

Миграция `12_competition_event_results` добавляет:

- `competition_event_result_sheet` — настройки и состояние зачёта мероприятия;
- `competition_event_result_entry` — индивидуальная или командная строка и рассчитанный итог;
- `competition_event_result_entry_application` — состав строки из одобренных заявок;
- `competition_event_task_result` — результат каждой задачи.

Существующие таблицы, поля и внешние ключи не изменяются. Новые таблицы нужны, потому что `competition_result` не хранит задачи, черновик, состояние утверждения или командный состав.
