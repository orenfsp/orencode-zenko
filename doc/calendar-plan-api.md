# API календарных планов

Модуль хранит официальные календарные планы и показывает соревнования, которые уже связаны с ними через `competition.calendar_plan_id`. Это административный API; он не заменяет публичный календарь `GET /api/v1/calendar/competitions` и не создаёт соревнования автоматически.

Базовый URL: `/api/v1`. Все описанные ниже endpoints требуют access-токен:

```http
Authorization: Bearer <access_token>
```

Успешные ответы имеют форму `{"data": ...}`, ошибки — `{"message":"Описание ошибки"}`. Без токена возвращается `401`, без нужного permission — `403`.

## Permissions

| Permission | Назначение |
|---|---|
| `calendar_plans.read` | просмотр планов и включённых соревнований |
| `calendar_plans.create` | создание плана |
| `calendar_plans.update` | изменение плана |

RBAC seed регистрирует permissions и назначает их системной роли `super_admin`. Для сотрудника федерации нужно создать или обновить подходящую роль существующим RBAC-механизмом и включить в неё нужные коды.

Для включения соревнования в план через Competition API роли также нужны уже используемые этим API `competitions.create` (создание) и `competitions.update` (изменение черновика). Они также регистрируются RBAC seed.

## Получение списка планов

```http
GET /api/v1/admin/calendar-plans?year=2026&limit=50&offset=0
```

Требуется `calendar_plans.read`.

Параметры:

| Параметр | Правила |
|---|---|
| `year` | необязательный положительный год в диапазоне PostgreSQL `smallint` |
| `limit` | от 1 до 100, по умолчанию 50 |
| `offset` | неотрицательное число, по умолчанию 0 |

Планы сортируются по году от новых к старым, затем по `id` по возрастанию.

```json
{
  "data": [
    {
      "id": 3,
      "name": "Календарный план Оренбургской области",
      "year": 2026
    }
  ]
}
```

Если записей нет, `data` содержит `[]`.

## Получение одного плана

```http
GET /api/v1/admin/calendar-plans/3
```

Требуется `calendar_plans.read`.

```json
{
  "data": {
    "id": 3,
    "name": "Календарный план Оренбургской области",
    "year": 2026
  }
}
```

Несуществующий план возвращает `404`.

## Создание плана

```http
POST /api/v1/admin/calendar-plans
Content-Type: application/json
```

Требуется `calendar_plans.create`.

```json
{
  "name": "Календарный план Оренбургской области",
  "year": 2026
}
```

Начальные и конечные пробелы в названии удаляются. После этого название должно содержать от 1 до 200 Unicode-символов. Год обязателен, должен быть положительным и помещаться в `smallint` (максимум 32767). Одинаковые название и год разрешены, поскольку в схеме нет соответствующего ограничения уникальности.

Успех: `201 Created` с созданным объектом в `data`.

## Изменение плана

```http
PATCH /api/v1/admin/calendar-plans/3
Content-Type: application/json
```

Требуется `calendar_plans.update`. Можно передать одно или оба поля:

```json
{
  "name": "Обновлённый календарный план"
}
```

```json
{
  "year": 2027
}
```

PATCH сохраняет значения отсутствующих полей. Пустой объект, явный `null`, поле `id` и любые другие неизвестные поля возвращают `400`. После объединения изменений применяются те же проверки названия и года, что при создании. Связанные соревнования автоматически не изменяются.

Успех: `200 OK` с обновлённым объектом в `data`. Несуществующий план возвращает `404`.

## Соревнования в плане

```http
GET /api/v1/admin/calendar-plans/3/competitions?limit=50&offset=0
```

Требуется `calendar_plans.read`. Сначала проверяется существование плана. Соревнования выбираются по `competition.calendar_plan_id`, сортируются по `start_at`, затем по `id`. Административный список не фильтрует статусы и поэтому включает `draft`.

```json
{
  "data": [
    {
      "id": 17,
      "name": "Чемпионат Оренбургской области",
      "start_at": "2026-04-10T07:00:00Z",
      "end_at": "2026-04-12T15:00:00Z",
      "status": "draft",
      "discipline": {
        "id": 1,
        "name": "Программирование алгоритмическое"
      },
      "calendar_plan_number": "12"
    }
  ]
}
```

Если план существует, но связанных соревнований нет, `data` содержит `[]`. Если плана нет, возвращается `404`.

## Связь с Competition API

Связь один-ко-многим хранится только в существующей таблице `competition`:

- `calendar_plan_id` — внешний ключ на `calendar_plan.id`; `null` означает отсутствие плана;
- `calendar_plan_number` — необязательный номер соревнования в плане;
- один план может содержать несколько соревнований;
- одно соревнование может относиться максимум к одному плану.

При создании соревнования сотрудник передаёт оба поля в существующий endpoint:

```http
POST /api/v1/competitions
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "name": "Чемпионат Оренбургской области",
  "description": "Описание",
  "discipline_id": 1,
  "competition_type_id": 2,
  "competition_level_id": 3,
  "format": "offline",
  "start_at": "2026-04-10T07:00:00Z",
  "end_at": "2026-04-12T15:00:00Z",
  "registration_starts_at": "2026-02-01T00:00:00Z",
  "registration_ends_at": "2026-04-01T00:00:00Z",
  "venue_address": "Оренбург",
  "calendar_plan_id": 3,
  "calendar_plan_number": "12"
}
```

Существующий Competition Service проверяет наличие указанного календарного плана. Несуществующий внешний ключ отклоняется как некорректная ссылка.

Для черновика связь меняется через существующий PATCH:

```http
PATCH /api/v1/competitions/17
```

```json
{
  "calendar_plan_id": 3,
  "calendar_plan_number": "12"
}
```

Для удаления связи достаточно явно очистить `calendar_plan_id`; Competition Service согласованно очистит и прежний номер:

```json
{
  "calendar_plan_id": null
}
```

Можно также явно передать `"calendar_plan_number": null`. Задать непустой номер одновременно с `calendar_plan_id: null` нельзя.

Competition PATCH разрешён только для статуса `draft`. Привязка уже опубликованного соревнования в рамках Calendar Plan API намеренно не обходится; для этого нужен отдельный будущий сценарий управления Competition с явно согласованными правами и правилами жизненного цикла.

## Коды ответов

| Код | Значение |
|---:|---|
| `200` | успешный GET или PATCH |
| `201` | план создан |
| `400` | неверный ID, JSON, поля, год или пагинация |
| `401` | отсутствует или недействителен access-токен |
| `403` | нет требуемого permission |
| `404` | календарный план не найден |
| `500` | внутренняя ошибка; детали PostgreSQL клиенту не возвращаются |

Конфликт `409` сейчас не используется: схема допускает одинаковые названия и годы, а других конфликтующих бизнес-правил у календарного плана нет.
